## Обзор

Доступ к MCP осуществляется через стандартную аутентификацию Redmine по API-ключу. Все операции выполняются от имени пользователя, которому принадлежит ключ.

## Цель

Гарантировать, что MCP не обходит систему безопасности Redmine и пользователь может выполнять только разрешённые ему действия.

## Затронутые области

- Permissions
- API
- Users

## Бизнес-правила

### Аутентификация

- Для доступа к `/mcp` должен быть включён REST API Redmine.
- API-ключ передаётся только в заголовке `X-Redmine-API-Key` (не из JSON-тела запроса и не из query string).
- Принимаются только ключи активных пользователей.
- При отсутствии или невалидном ключе запрос отклоняется.

### Глобальное право MCP

- Пользователь должен иметь глобальное право **Use MCP** (`use_mcp`), либо быть администратором Redmine.
- Право `use_mcp` включается вручную у нужных ролей в **Администрирование → Роли и права**.
- Администраторы имеют доступ к MCP всегда: стандартная глобальная проверка прав Redmine разрешает admin независимо от ролей.
- Для остальных пользователей без `use_mcp` запрос отклоняется, даже при валидном API-ключе.

### Права на инструменты

- Каждый инструмент имеет собственное требование к правам Redmine.
- Инструмент отображается в `tools/list` только если пользователь имеет право на его использование.
- При вызове инструмента права проверяются повторно.
- Данные фильтруются по правилам видимости Redmine (проекты, задачи, участники).

### Права на ресурсы и промпты

- Ресурсы и промпты могут иметь собственные требования к правам.
- При отсутствии прав ресурс или промпт не отображается в списке и недоступен для чтения.
- Проверка прав ресурса и промпта учитывает URI и входные аргументы (в том числе `project` / `project_id`). Если проект в аргументах не задан, достаточно права хотя бы в одном видимом проекте.
- Расширение может задать явное правило определения проекта из URI и аргументов.

## Граничные случаи

- Неактивный пользователь не может использовать MCP, даже с ранее выданным ключом.
- Администратор имеет доступ к MCP без отдельного назначения `use_mcp`.
- Инструмент с проверкой прав по конкретной сущности (например, задаче) при пустых аргументах в `tools/list` может быть виден, если пользователь имеет соответствующее право хотя бы в одном проекте.
- Если для такого инструмента дополнительно задано требование модуля проекта Redmine, «хотя бы один проект» означает видимый проект, где одновременно есть это право и включён указанный модуль. Без требования модуля достаточно права хотя бы в одном видимом проекте. Наличие инструмента в `tools/list` не означает разрешение на операцию над конкретной задачей: при вызове права и доступность объекта проверяются повторно.

## Обработка ошибок

| Ситуация | Результат |
|----------|-----------|
| REST API выключен | HTTP 401 |
| Неверный или отсутствующий API-ключ | HTTP 401 |
| Нет права Use MCP | HTTP 403 |
| Нет права на конкретный инструмент | Инструмент отсутствует в `tools/list`; при прямом вызове — ошибка «Permission denied» |
| Сущность недоступна пользователю | Ответ инструмента с описанием ошибки (например, «Issue not found») |

## Тестовые сценарии

1. Запрос с валидным ключом и правом Use MCP — успешный доступ.
2. Запрос без заголовка API-ключа — HTTP 401.
3. Запрос с ключом не-администратора без права Use MCP — HTTP 403.
4. Запрос с ключом администратора без роли с `use_mcp` — успешный доступ.
5. Пользователь видит в `tools/list` только инструменты, на которые у него есть права.
6. Вызов инструмента для недоступной задачи возвращает ошибку, а не данные другого пользователя.
7. Инструмент с областью задачи и требованием модуля проекта не виден в `tools/list`, если у пользователя есть право, но нет ни одного видимого проекта с включённым модулем; виден, если такой проект есть.
